# v3.40.2 —— 修回 README 的编码错误（从最后一个干净版本还原）

> 反馈「介绍文件的编码错误」。查下来是**两个 README 从 v3.26.0 起一直是乱码** ——
> GitHub 上看着"排版有点怪"，但没人会逐字读，所以一直没人报。

## 一、病因（查到具体提交，不是猜）

写坏它的是 **`0301352a`（v3.26.0）**：那次提交对两个 README 是 `+90/-90` 与 `+199/-199`
—— **整文件被重写**。这正是"UTF-8 被按 GBK 读进来、再按 UTF-8 存回去"的特征，
也就是中文 Windows 控制台上 `Get-Content ... | Set-Content ...` 的经典后果：

| 原本 | 变成 |
| --- | --- |
| 破折号（E2 80 94） | 鈥? |
| 间隔号（C2 B7） | 路 |
| 中文（E4 B8 AD E6 96 87） | 涓枃 |
| 右箭头（E2 86 92） | 鈫? |

少数位置还**丢了字节**（在文本里留下一个 ASCII `?`），所以"按 GBK 编回去再按 UTF-8 解"
只能救回大部分 —— 逐字猜不是好办法。

## 二、修法：从最后一个干净版本还原

三条证据说明这样修是**无损**的，不会把后来有意加的文档内容一起回退：

1. `git log --numstat`：v3.25.0（`d3ac97fd`，最后一个干净版）之后，两个 README **只在
   版本徽章那一行**被改过 —— 每个提交都是 `+1/-1`；唯一一个 `+2/-2` 是顺手去掉了 BOM；
2. 把干净版与乱码版按 **ASCII 骨架**对齐（非 ASCII 一律抹成 `~` 再比）：**行数完全一致
   （288 / 340 行），没有插入行、没有删除行**；
3. 写坏的提交与之后的所有提交都没动过正文结构。

于是：`git show d3ac97fd:README.md` → 写回 → 把徽章版本补到当前版本。两个 README 都这么做。

## 三、防复发：新增测试段 `[68]`

| 断言 | 为什么 |
| --- | --- |
| 全仓被跟踪的文本文件**不许出现成串的乱码特征字符**或替换符 | 这次坏的是 README，同一个手滑能坏任何文档 |
| 两个 README 干净且**不带 BOM** | BOM 会让首行渲染出多余字符（那次 `+2/-2` 就是在删它） |
| **README 徽章版本 == `core/version.py`** | 介绍文件挂着旧版本号，比乱码更常见 |
| 恢复依据留在 CHANGELOG 里 | 下次有人再遇到，能直接照着复核 |

豁免用**行数预算**而不是"整文件跳过"：讲乱码本身的文档允许引用少量样例（≤6 行），
但整文件被写坏时行数会爆掉 —— 照样抓得到。

## 四、和 v3.40.1 的关系

v3.40.1 修的是**运行时**编码（cp936 控制台下 emoji 崩 / 字形花屏）；
这一版修的是**仓库文件**编码。根因相同（UTF-8 与 GBK 互相错读），但一个在输出路径上、
一个在文件内容里，验证方式也不同：

- v3.40.1：`PYTHONIOENCODING=gbk` 真跑三个入口，要求退出码 0；
- v3.40.2：全仓扫乱码 + 徽章与版本单源一致（纯静态检查，任何平台都能跑）。

> 把安全的**对象**从"命令/工具名"换成"世界的三条性质"：**世界可重建（I1）· 意图可归属（I2）·

## 2. 语言与组件决策（先定这个）

**决定：不引入任何新语言，不引入 C++。**

| 做什么 | 用什么 | 为什么 |
|---|---|---|
| 判定、策略、台账、授权令、来源归属 | **Python（纯 stdlib）** | 与执行层同一个进程、同一套 `test_all` 纪律；HMAC/JSON/路径判断都在 stdlib 里，零新依赖 |
| 纯计算（指纹、哈希、去重、事件索引） | **已有的 Rust `engine/`** | 它今天的边界就是"只算不裁"（`engine/README.md`）；扩大它的角色＝破坏这条边界，所以**只**接纯计算 |
| 真需要**进程边界**时 | **已有的 Go `executor/`** | Job Object / 容器已经在那一侧；不另造一个"内核进程" |
| 影子平台的廉价复制（若 RG-05b 通过成本门） | **Python + `ctypes`** 调 ReFS 块克隆 | 一个 API 调用，不需要新工具链；Rust 侧只做指纹 |

三条**否决**理由，写下来免得以后有人再提：

1. **不新增语言**：ACE 已经有三套（Python / Rust / Go）且各有明确边界；第四套只会带来第四条发布链
   （又一条"本地不可验证"的路，本仓库在这上面已经红过五次）。
2. **不用 C++**：这里没有性能诉求需要它（真需要就把活交给已有的 Rust 引擎），而它会引入构建工具链、
   ABI、跨平台发布三个新变量。
3. **不把"内核"写成又一个 Python 模块**：agent 与执行层**同进程、同用户**，同进程的东西不构成信任边界
   （见 §3）。

## 3. 座位（seat）在哪 —— 本卡对原方案最大的一处修改

原报告的核心主张之一是"席位分离"：承载信任的机制必须住在被信任对象够不着的地方。
今天 ACE 的实情（已核实）：

- `core/guardian.py:91`：`self.store = project_root / ".guardian"` —— **在项目目录里**；
  `:101-106`：签名密钥落在 `.guardian/signing_key`。
- `core/sensitive.py:92-98`：`AGENT_STATE_DIRNAMES = {".guardian", ".ace_sessions", ".agent_flywheel",
  ".poc_reports"}`，理由原文就是"agent 改一行 `meta.json` 就能让 `verify_snapshot` 失效"。
- `tools/file_ops.py:102` → `_resolve_target_path` → `sensitive_target`：**读写都过这道判据**
  （`test_all.py:1889/1912` 有断言）。这道守卫是 2026-09-25 的 `b6aeede` 进来的。

**结论**：今天保护信任锚的是一道**路径判据**，而路径判据正是本方案论证"补不全"的那一类东西。
但**修法不是写一个内核模块**：

> 座位 = **工作区之外的、由操作系统权限保护的状态目录**（数据层），加上**已有的进程边界**
> （需要在同一进程里做不了的事时，走 `executor/`）。

同用户、同进程的 agent，靠文件位置**不能**获得绝对边界 —— 这一点必须写在文档里而不是含糊过去。
真正的边界仍是"agent 够不着工作区外"这条**执行层的既有约束** + OS ACL；进程隔离是加强项，不是本卡的前提。

### RG-01 · 信任锚外移（S）—— **已实施**

- **改动**：`core/guardian.py` 的密钥路径解析改为**工作区之外的锚目录**
  （Windows `%LOCALAPPDATA%\ace-agent\state\<sha256(项目绝对路径 normcase)[:16]>\signing_key`；
  POSIX `$XDG_STATE_HOME` 或 `~/.local/state` 同构），根目录可用构造参数 `anchor_dir` 或
  环境变量 `ACE_ANCHOR_DIR` 注入。**快照仍留在 `.guardian/snapshots/`**（那是数据不是锚）。
- **实施记录（含对规划的一处修正）**：
  1. 规划里写的是"旧密钥保留但不再使用" —— **错**，已改为**搬完即删**。只拷不删等于把同一把密钥
     继续留在 agent 可写处，锚白搬（这正是"实测比设计更有话语权"的一例：先写了探针才看出来）。
     删除前先写锚 + 读回校验；删不掉就大声告警（此时边界并未真正建立）。
  2. 锚不可用时 `snapshot()` **直接抛错拒绝**（走执行层既有的"快照不可用 → 503"），
     而不是生成一份未签名快照 —— 未签名快照的摘要可以随内容一起被改，等于把安全网变装饰。
  3. 另补一处 fail-open：快照**带签名**、而当前拿不到密钥时，`verify_snapshot()` 从原来的
     "跳过签名只比摘要"改为**直接拒绝**（原文：拿不到密钥就说拿不到）。
  4. POSIX 下密钥文件 `chmod 0600`（Windows 靠 `%LOCALAPPDATA%` 的 ACL）；设不上只告警不中断。
- **验收（可证伪，全部已落地为 `test_all` 段 `[71]` 的 RG-01a~g）**：
  1. 迁移：`anchor_migrated=True`、锚里是同一把密钥、**项目内那份已不存在**；
  2. 迁移后老快照 `verify_snapshot` 仍为 true；
  3. 锚路径不以项目路径为前缀；
  4. **伪造不成立**：改副本 + 修 `meta.json` 摘要 → 仍判坏快照（项目内已无密钥可重签）；
  5. 攻击者自带一把密钥重签 → 仍不通过（锚里那把才是真的）；
  6. 拿不到密钥时拒绝验证带签名的快照；
  7. 锚不可用 → `snapshot()` 抛 `SnapshotError`（fail-close）。
- **可运营性（2026-09-26 深化）**：锚现在是**硬依赖**（不可写 → 写操作 fail-close），所以
  `python -m cli.ace_doctor` 增加信任锚体检：报锚路径与已有哪些密钥、锚根来自默认还是
  `ACE_ANCHOR_DIR`、**锚是否落在工作区内**（与设计相反时告警）、**项目内是否还残留旧密钥副本**
  （"搬了等于没搬"的那种）、POSIX 下密钥文件权限是否过宽。断言 `RG-01h` 钉住它真的报出来。
- **实测对照（探针 `e2e/rg_probes.py rg01`）**：修复前"改内容+修摘要+用项目内密钥重签"
  → `verify=True`（安全网可伪造）；修复后同一操作 → `verify=False`（签名校验失败）。
- **顺带修正的文档**：`docs/SECURITY-AUDIT.md` 的 SEC-010 记录描述的
  `resolve_signing_key()` / `ACE_SIGNING_KEY` / `~/.ace/snapshot_signing_key` /
  `get_stats()["snapshot_signing"]` **在代码里 0 命中**，而实际把密钥放在了项目内 ——
  该段已加勘误（描述的设计未落地，且与代码事实相反）。
- **风险**：低。**回滚**：`git revert` 该提交（迁移只搬不删旧快照，锚里的密钥是数据的副本）。

### RG-02 · 事件台账链式签名（S）

- **改动**：`cli/ace_sessionlog.py` 每条事件加 `mac = HMAC(anchor, seq ‖ prev_mac ‖ canonical(body))`；
  `/audit` 增加整链校验；`seq` 断裂检测已有（`test_all` E4）。
- **验收**：
  1. 改一行内容 → 链断，且指出是哪条 `seq`；
  2. 删中间一条 → `seq` 断 + 链断；
  3. 尾部追加伪造行 → 无法生成有效 `mac`；

### RG-02 · 事件台账链式签名（S）—— **已实施**

- **改动**：`cli/ace_sessionlog.py` 每条事件带 `mac = HMAC(台账密钥, prev_mac ‖ 该条正文)`；
  正文按"排序键 + 紧凑分隔符"规范化（`_canonical_body`），所以键序变化不影响校验。
  台账密钥从**同一个锚**派生（`<锚>/sessionlog_key`，再 HKDF 式的域分离 `ace-sessionlog-v1`），
  与快照签名密钥**分开**：各用各的，互不牵连。`sessions.md` 与 `ai_code.py` 的
  `/audit stats` 增加整链校验行（三态：ok / broken / unverifiable）。
- **实施记录**：
  1. 校验接口返回**三态**而不是布尔：`"ok"` / `"broken"` / `"unverifiable"`（老日志或拿不到密钥）
     / `"empty"`。把"验过了没问题"与"根本没法验"混在一起，是这类机制最常见的失效方式。
  2. **一处刻意的偏离**：台账密钥不可用时**不 fail-close**，而是照写、打一次告警、
     校验如实报 `unverifiable`。理由：台账是**记录**不是闸门 —— 因为写不了签名就让整轮对话挂掉，
     换不来任何安全收益（攻击者本来就能删掉整份日志）。这与快照（闸门，必须 fail-close）不同，
     所以两条路故意不一样，且都写在代码注释里。
  3. 被既有测试抓到一次回归：`append()` 里**先算 MAC 后验序列化**，把"不可序列化 payload 抛
     `ValueError`"这条既有契约换成了 `TypeError` 漏出。已改为先兑现深冻结契约再算 MAC。
  4. **体检挪到恢复那一刻**（2026-09-26 深化）：`chain_notice()` 挂在 `_switch_session`（`/resume`
     等）与启动自动续聊两处 —— 恢复动作正是把那份记录**读进上下文**的一刻，早一秒知道就少一分
     "拿被改过的记录当事实"的机会。三态处理写死在函数里并各有断言：`broken` → 告警；
     `unverifiable` 但**本来带签名**（拿不到密钥）→ 告警；**老日志（整份无 mac）→ 静默**
     （那是历史，每天喊一次只会让人学会忽略告警）；`ok`/`empty` → 静默。
- **验收（`test_all` 段 `[71]` 的 RG-02a~g + H + i）**：
  a 正常日志整链 ok 且每条带 mac；b 改内容 → broken 并指出第几条；c 删中间一条 → broken
  （不只是 seq 缺口）；d 剥掉某条的 mac → broken；e 尾部追加伪造 → broken（**seq 连续也照样抓到**）；
  f 老日志（无 mac）→ `unverifiable`，不冒充 ok 也不冤枉成 broken；g 密钥不可用 → 不炸 + `unverifiable`；
  i/i2 **显示**这一半也验：`/audit stats` 真的打出 ok 行、台账被改后打出 broken 行
  （上一轮 I5/I6 的教训：只测记录不测显示，等于没测用户看到的东西）。
- **实测（探针 `e2e/rg_probes.py rg02`）**：三个真攻击形状——改 `permission/decision`
  （deny→allow）、删中间一条、尾部追加伪造事件——修复前 `seq_contiguous()` 只抓得到第二个，
  日志里**没有任何字段**能说明被动过；修复后三条全部 `verify_chain() = broken` 并指出位置。
- **开销（量出来的，不是"应该很快"）**：单条 MAC 计算 **6.5 µs**；`append` 整条路径 **11.4 ms/条**，
  其中绝大部分是**既有的** `os.fsync`（本次新增的不是它）。
- **风险**：低。**回滚**：`git revert` 该提交；旧日志（无 mac）本就被判 `unverifiable`，不会误伤。

### RG-04 · 可逆性分类器（M 测量版；翻判另开 RG-04b）—— **第一阶段（分类器）已实施**

### RG-05a · 授权令（M/L）—— **第一阶段（令本身）已实施**

**粒度换向**：ACE 今天的审批粒度是**对象**（H-09：一次调用绑一个对象），弹窗数随危险步数
线性增长。原型的主张是换成**一次任务一张令** `(intents, roots, recoveryFloor, irreversibleQuota, ttl)`，
签名用**锚里的密钥**（RG-01 那个座位）；之后每次行动只是对着令核一遍 → 弹窗 O(步数) → O(任务数)。

**第一阶段只做令本身**，`_stage_permission` **一行都没动**（与 RG-03/RG-04 同节奏：先逻辑与
可证伪测试，接入审批流程是下一步，那一步才会真的改变弹窗行为）。新增 `core/ace_mandate.py`：

- `issue()` 签一张令（含 `issuedAt`/`expiresAt`/`usedIrreversible`），`verify()` 返回**三态**
  `ok` / `invalid` / `expired`；`authorize()` 是**纯函数**，四条判定按顺序给出
  `allow` / `escalate` / `deny`；`record_use()` 累加额度并**重新签名**（不重签等于额度可事后随便改）。
- 口径（都写进模块 docstring，免得以后各处理解不一）：
  1. **可逆性从强到弱 `GIT > SNAPSHOT > REGENERABLE > UNKNOWN > NEVER`** —— "可再生"比
     "有快照"弱一档（重装依赖未必同版本）；
  2. **过期 = 升级**（重签一张即可），**签名不符 / 缺签名 = 拒绝**（令被改过时问人没有意义：
     人也只能看到一张被改过的纸条）；
  3. 目标**没有分类信息**时按 `UNKNOWN` 处理（保守）；`NEVER` 类永远达不到任何下限，只能靠
     `allowIrreversible` 点名 + 额度。
- **验收（`test_all` 段 `[71]` 的 RG-05a~i）**：a 令内且达标 → allow；b 越出 roots → escalate；
  c 未授权的工具 → escalate（intent_scope）；d **改 roots 保留原签名 → deny**；e 过期 → escalate；
  f 点名放行的不可逆动作 → allow 且消耗 1；g 额度累加后重新签名（旧签名对不上）；h 额度用尽 →
  escalate（quota_exhausted）；i 低于下限且未点名 → escalate（recovery_below_floor）。
- **风险**：低（新增纯逻辑模块，未接入任何判定路径）。**回滚**：`git revert` 该提交。

### RG-05a-2 · 把令接进审批流程（M）—— **已实施（默认不配令 = 行为不变）**

`_stage_permission` 里加了 `_mandate_decision()`，挂在**两处"问人"之前**：

- 项目外**已存在**对象的确认（`_outside_destructive_reason` 命中处）；
- `CONFIRM_TOOLS`（实测 = `edit_file` / `terminal_exec`）的逐次确认。

**令能做什么、不能做什么**（这是本步最关键的设计判断，都写在代码注释里）：

| 轴 | 令能否覆盖 | 理由 |
|---|---|---|
| 项目外对象确认 | ✅ 能（roots 覆盖即可） | 这正是"一次任务一张令"要收拢的 O(步数) 弹窗 |
| `CONFIRM_TOOLS` 逐次确认 | ✅ 能，但**必须在 `allowIrreversible` 里点名**并消耗额度 | 这类工具的痕迹**不可枚举**（目标是命令不是路径）→ 按不可逆处理 |
| 持久规则 deny / 未注册 MCP / 工具自身的敏感目标判定 | ❌ **不能** | 硬拒绝；问人没有意义（`RG-05o` 钉住：未注册 MCP 工具即使被令点名也是 503） |
| 外发确认（egress） | ❌ 不能 | **另一个轴**：那是"能发到哪去"，令管的是"能动哪些对象" |
| 权限等级不足 | ❌ 不能 | 与既有先例一致：`/rules` 的 allow 也不提权（想放开请显式升级等级） |

**一处刻意的偏离与它的理由**：令**无效/过期/被篡改**时**不是**拒绝这次调用，而是**回落成照旧问人**
并把原因告警一次（事件记 `mandate_invalid`）。理由：配了一张坏令不该把正常工作变成 403；
但更不能把它当绿灯 —— 所以是"回落"（fail-safe），而不是"放行"或"拒绝动作"。

- 新增 `cli/ace_mandate.py`（操作者工具）：`issue` 签令 / `show` 检查，密钥从**锚**派生
  （与快照、台账域分离）；签出来的 JSON 贴进配置的 `"mandate"` 键即生效。
- **验收（`test_all` 段 `[71]` 的 RG-05j~o）**：j 没配令 → 与以前逐字相同（仍然问人）；
  k 有效令覆盖项目外对象 → 不再问人（事件 `mandate_allowed`）；l 消耗额度且令被重新签名；
  m 令不覆盖该工具 → 照旧问人；n 令被篡改 → 不说放行，回落问人 + `mandate_invalid`；
  o 硬拒绝不受令影响（未注册 MCP → 503）。
- **收益验收（实测，`e2e/rg_probes.py rg05`）**：同样 5 次"项目外已存在文件"的写 ——
  **不配令 5 次逐次确认 → 配令（roots 覆盖 + 额度 5）0 次**；而**配额只给 2 时仍有 3 次确认**
  （额度是**真边界**，不是橡皮图章）。这就是"弹窗 O(危险步数) → O(任务数)"的直接证据：
  人只在**签令那一刻**参与一次。
- **风险**：中（改的是审批路径，但**默认关闭**：不配 `mandate` 键时走的是原来的分支，
  `RG-05j` 就是钉这一点的）。**回滚**：`git revert` 该提交，或把配置里的 `mandate` 删掉。

### RG-05b · 影子平台（L）—— **G3 门未过：实测后决定不做**

**先量再决定，结果是不做。** 实测（`e2e/rg_probes.py rg05b`，真实工作区，已跳过构建/缓存/状态目录）：

| 项 | 实测 |
|---|---|
| 工作区规模 | 1008 文件 / 23.8 MB |
| 复制 | 1639 ms |
| **指纹（冷，刚复制出来的副本）** | **10 062 ms** |
| 指纹（热，同一批再读一遍） | 681 ms |
| **单次动作估算（复制 + 前后各一遍冷指纹）** | **11.6 ~ 21.8 s**（两次独立实测；冷读本身波动大） |
| G3 门槛 | 300 ms → **超 39 ~ 73 倍** |
| 工作区所在卷 | **NTFS** |

- **机制说清楚**：成本的大头**不是复制**（1.6 s），而是**刚写出来的副本第一次被读**
  （单次约 10 s ≈ 10 ms/文件）—— 与立项时 guardian 那边测到的"冷读 24 ms/文件、热读 0.07 ms/文件"
  是同一件事；影子每次动作都要付两遍这 10 s。两次实测的区间（11.6 ~ 21.8 s）差在冷读那一段，
  所以**引用时给区间**，别只挑一个数。
- **没有廉价写时复制这条替代路**：Windows 上只有 **ReFS** 才有块克隆（`FSCTL_DUPLICATE_EXTENTS_TO_FILE`），
  本机工作区在 **NTFS** 上。overlayfs/APFS clone 在 Linux/macOS 才存在。
- **因此本卡不实现影子**，理由与数字都在上面。这符合立项时就写下的结局："先过成本门，不达标就不做"。
- **门是**可执行的**记录**：`rg05b` 的断言写的是"估算成本 > 门槛 → 判不做"。所以**换到 ReFS/Linux
  且实测达标时它会红** —— 那不是回归，是提示"G3 的前提变了，决策要重看"。
- **与它无关但同样要写死的一条**：即使将来做了影子，也**不依据影子放开任意代码执行**。
  原型的外部落点检测是"对 argv 做正则"（`rgtc_kernel.js:705-726`），运行时拼出来的路径
  （`os.homedir()`、`process.env.TEMP`）看不见 → 会把"写到了工作区外"判成"可逆且在范围内"。
  所以 `_FORBIDDEN_RULES` 里 `python`/`npm` 那条**保留**，直到有真正的强制层（容器/overlay）。

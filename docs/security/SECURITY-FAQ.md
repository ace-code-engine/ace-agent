# 安全边界 FAQ

> 这份 FAQ 只回答一类问题：**HooH 挡住了什么、没挡住什么。**
> 每条答案都能在代码、断言或实测记录里找到依据；拿不准的地方**直接写"拿不准"**，不写一句听起来很安全的承诺。
>
> - 完整安全模型与生产部署要点：[`SECURITY-MODEL.md`](SECURITY-MODEL.md)
> - 逐条审计与证据：[`SECURITY-AUDIT.md`](SECURITY-AUDIT.md)
> - 漏洞上报流程：[`../SECURITY.md`](../../SECURITY.md)
>
> **一句话前提**：HooH 把"能不能动"从提示词搬进了执行层。但**执行层本身没有 OS 级隔离** ——
> 真正不可越过的边界是**沙箱档（`--sandbox job` / `--sandbox docker`）+ 最小权限账户**。
> 下面每一问都建立在这句话上。

---

## 1. 模型被越狱 / 提示注入成功了，会怎样？

**它拿不到新的权限。** 每次工具调用都要过执行层：权限档、AST 行为检查、路径边界、出站清单与逐次确认 ——
这些**都不由模型的输出来决定**。所以"说服模型"和"让工具真的跑起来"是两件事。

但这**不等于安全**：模型仍能调用**你当前权限档允许**的工具。`readonly` 档下它读不到项目外的东西；
`full` 档下它能做的事，就是你在 `full` 档下允许的事。

一处容易被忽略的设计：授权**绑定具体对象**，不是绑定工具名 ——
"批准一次 `terminal_exec`"不等于"这个会话里 `terminal_exec` 全开"（H-09）。

---

## 2. 我不用 `--sandbox`，安全吗？

**问题不是"安全 / 不安全"，而是"边界落在哪一层"。**

| 层 | HooH 做了什么 |
|---|---|
| 提示词 | 只引导模型，**不承诺任何东西** |
| **应用层（默认开）** | 执行层策略：三级权限、AST 行为检查、写前快照与回滚、路径边界、SSRF 与出站清单、**逐次出站确认**（含"项目外覆盖/删除 ⇒ 问人"） |
| OS 层（可选，仅 Windows） | `--sandbox job`：Job Object 进程/内存上限 + 受限令牌 |
| 容器层（可选） | `--sandbox docker`：一次性容器、`network none`、`cap-drop ALL`、只读根、`--init`，只挂载工作区 |

不用沙箱档时，**第 2 层（应用层）仍然全效**。它挡得住：凭据文件、项目外路径、需要确认的写、出站到未允许的目的地。
它**挡不住**：`terminal_exec` 里复杂或多步拼装的行为，以及 `code_execute` 里静态分析枚举不完的构造（见第 7 问）。

---

## 3. `--sandbox job` 和 `--sandbox docker` 差在哪？容器算隔离吗？

- **`job`**：**Windows 独有**。用 Job Object 限进程数与内存，再加受限令牌。
- **`docker`**：一次性容器，`network none`、`cap-drop ALL`、只读根、`--init`，只把工作区挂进去。
- **容器与宿主共享内核 —— 逃逸仍然是逃逸。** HooH **不**宣称 docker 档是"绝对隔离"。
- 沙箱镜像默认**本地构建**（`docker/Dockerfile.sandbox`）；`ACE_SANDBOX_PULL=1` 可拉预构建镜像，
  但那意味着你多信任了 registry 那条链。

---

## 4. 沙箱档不可用时，会不会偷偷退回宿主？

**不会。** `job` / `docker` 在边界不可用时返回 **503**，**绝不静默回退到宿主**。

这条是硬承诺，不是文档口号：`tools/status.py` 把 503 定义为"沙箱档不可用（**不静默回退**）"，且它是**唯一来源**（散落的错误码字面量会被 AST 守卫拒绝）。

同理，`code_execute` 在**没有 OS 边界**时返回 503，而不是"尽力执行"（H-30）。

---

## 5. 无人值守 / CI 里，什么会被拒、什么照跑？

**这一点与直觉相反，值得单独记：**

- **需要审批的动作 → 直接拒绝。** `terminal_exec`、外发确认、项目外覆盖确认在非交互环境里**走不通**。
- **不需要审批的写 / 执行工具 → 照跑。** `file_write` / `code_execute` / `api_post` … 只受进程内策略约束。

所以要跑无人值守，**必须显式**给 `--sandbox job` / `--sandbox docker`（可配 `--approval-policy on_failure`），
或从 `readonly` 起步。

> ⚠️ **fail-close 的是"要问人的那些"，不是"危险的那些"。**
> 别把"CI 里没报错"读成"CI 里很安全"。

---

## 6. 出站闸门管住了什么、没管住什么？

**管住了**：**模型自己选的目的地**。不在内置清单、也不在你的 `egress_allowlist` 里的目的地，**逐次确认**；
**会话级授权被拒绝** —— 按工具名给授权等于出口全开，所以这条路被堵死。

**没管住**（写在这里，而不是藏起来）：

- **内置端点**（搜索引擎、图片服务）**不逐次确认**；
- `image_generate` 会把提示词**明文**发给第三方服务。

---

## 7. 静态检测（AST / execpolicy）能挡住多少？

**能抬高成本、挡住已知形态，但枚举不完。**

`code_execute` 的 AST 引用级拦截、`execpolicy` 的命令判定、出站清单，都是**模式 / 静态层**。
复杂或多步拼装的恶意行为**不在射程内**。

这**不是待修的缺陷，是设计边界** —— 真正的边界是 OS / 容器档 + 最小权限账户。

---

## 8. 快照能回滚一切吗？

**不能，而且"不覆盖哪些"是刻意列出来的。** 快照**排除**：

- `.git` / `.guardian` / `.ace_sessions` / `.agent_flywheel`（版本库自身与 agent 自身状态 —— 回滚安全网本身不能被回滚）
- **凭据文件**（`.env` / `*.pem` 等按名单排除，**明文不进快照**，只记哈希）

所以它们**删了就是没了**。`core/ace_recovery.py` 的可逆性分类器把它们判成 `NEVER`，正是这个原因。

可逆性分类共五级：

| 等级 | 含义 |
|---|---|
| `GIT` | 在版本控制内（`git ls-files` 说了算）→ 可重建 |
| `SNAPSHOT` | 不在 git，但写前快照能覆盖 → 可回滚 |
| `REGENERABLE` | 依赖 / 构建产物类目录（**白名单**，不是"被忽略就算"）→ 可重新生成 |
| `NEVER` | `.git` / agent 状态 / 凭据 / 设备 / 工作区之外 |
| `UNKNOWN` | 说不清 → 若开判据就该问人 |

> 一条踩过才写下的口径：**"被 gitignore" ≠ "可再生"。**
> `docs/` 里的私有笔记、`secrets/`、`*.local` 都是 gitignore 的，但删了不可重建 —— 所以忽略状态一律判 `UNKNOWN`。

## 9. 凭据会被读走、或写进日志吗？

- **读**：凭据文件在只读路径判定里被拦（`core/sensitive.py`）。H-29 修掉了一处"`cat` 挡、`ls` 放"的漏 —— 现在两者用**同一个判据**。
- **快照**：凭据不进快照（按名单排除，只记哈希）。
- **台账**：审计台账会记录**工具调用与参数**。所以如果你把密钥写在命令行参数里，**它会进台账**。
  → **用环境变量或配置文件，不要写在命令里。**
- **前端**：`ChoiceDialog` 曾明文回显 API key（`getpass` 只在无 UI 时生效）——
  见 [`ROADMAP.md`](../ROADMAP.md) §3.3 的根因表，这是已登记待修项。

## 10. 这份安全文档可信吗？

**它是自评，不是第三方审计。**

`docs/SECURITY-AUDIT.md` 的结论逐条有证据，其中**可自动化的 payload 已钉成断言** ——
`python test_all.py --only 40`（安全审计 payload 回归，覆盖 SEC-003/006/007/010/014/018/019）。
但**没被断言覆盖的结论，仍然只是当时的实测记录**。

生产使用前请走自己的安全评估与红队演练（可以拿审计报告里的 payload 清单当起点）。

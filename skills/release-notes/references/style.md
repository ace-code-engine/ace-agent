# 分类与文风判据（release-notes）

## 分类（按用户影响排，不按 commit 数排）

| 分类 | 收什么 | 不收什么 |
|---|---|---|
| **破坏性变更** | 删除/改名公开 API、改变默认行为、配置键改名、数据结构不兼容、最低版本要求提高 | 内部函数改名、日志文案调整 |
| **新功能** | 用户能**做到**以前做不到的事（新命令、新参数、新工具） | 单纯的内部重构、为将来铺路的死代码 |
| **改进** | 同一件事变得更快/更稳/更清楚（可感知的） | 无用户可感知差异的重写 |
| **修复** | 用户遇到过的错误行为被纠正（写明症状，不写"修复若干问题"） | 只在测试里出现的失败 |
| **内部** | 依赖升级、CI、文档、重构、测试 | 上面四类里能归位的 |

判据一句话：**"用户会不会因此改变他的行为？"** 会 → 前三类；不会 → 内部。

## 文风

- 一行一条，动词开头，说清影响面：`新增 /foo 命令（--json 输出）`，不写 `添加了 foo 功能`。
- 症状优先于原因：`修复 Windows 下 --serve 首次连接失败`，而不是 `修复一个竞态`。
- 不写营销词：`全面升级 / 体验优化 / 大幅提升` 一律删掉，换成可核对的事实。
- 破坏性变更必须三段式：**变了什么 → 谁会受影响 → 升级要做什么**。
- 数字只在有出处时写（脚本实测、issue 编号、commit）；没出处就不写数字。

## 取材（只认这两处）

1. `git log --no-merges --oneline <range>` —— 意图（commit message）；
2. `git diff --stat <range>` + 关键文件 diff —— 事实（到底改了什么）。

两者冲突时以 **diff 为准**（commit message 会写错、会夸大）。
